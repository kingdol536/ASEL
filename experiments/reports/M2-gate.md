## 2. 테스트 결과

- 자동 테스트 **66개 통과** (M1 39개 → 66개).
- 새로 추가된 검증:
  - 공개 로그에 숨겨진 키(`duration`, `action_private`)와 실제 처리 시간 값이 나타나지 않음
  - 공개 로그만으로 재생하면 구조·시각은 같고 숨겨진 값은 비어 있음
  - 처리 시간을 공개 params 로 넘기면 거절
  - 급증 구간 도착 수 ≈ 2배 (시드 20개 합계, 허용 범위 1.6~2.5배)
  - 급증·고장 시나리오에서도 정책이 달라지면 같은 수요·처리 시간 (대응 비교 전제 재확인)
  - 고장 구간에 해당 셀에서 새 작업 시작 없음, 복구 후 재개, 진행 작업은 고장을 넘어 완료되는 사례 존재
  - 고장 원인·계획 종료 시각이 공개 로그·뷰어에 없음
  - 일괄 실행: 순차와 병렬의 집계표 동일
  - 뷰어: 비공개·시나리오·최종 상태 파일을 지워도 동작, 로그를 바꾸지 않음, 타임라인 구간 = 실제 상태

## 3. 측정된 증거

### 3.1 일괄 실행 (시나리오 3종 × 시드 0~29 = 90회)

시드 30개는 **임시 값**이다. 효과 분산·목표 정확도로 정한 표본 수가 아니다 (EXP-001 에서 결정).

| 항목 | 값 |
|---|---|
| 불변조건 위반 | **0** / 90회 (매 단계 검사) |
| 재생 검증 (공개+비공개 로그 → 최종 상태) | **90 / 90 일치** |
| 집계표 순차(jobs=1) vs 병렬(jobs=6) | **바이트 동일** (sha256 `3b87af1b…89f9e`) |
| 처리량, 순차 | 16.1 s, **335.9 runs/min**, 10,613 events/s (로그 쓰기·git 조회 포함) |
| 처리량, 병렬 6 프로세스 | 4.2 s, **1,294.8 runs/min**, 40,913 events/s |
| 순수 시뮬레이션 시간 합(순차) | 6.5 s → 실행 시간의 약 60% 는 파일 쓰기·manifest·git 조회 |

환경: Windows 11, Ryzen 5 7600 (12 스레드), Python 3.13.5.

### 3.2 시나리오별 단순 집계 (평가 지표 아님)

평가 지표는 미결정이다. 아래는 상태별 작업 수만 센 기술 통계다. "완료"는 주문이 아니라 작업(pick+pack) 단위다.

| 시나리오 | 완료 작업 평균 (표준편차) | 종료 시점 대기 작업 평균 / 중앙값 / 최대 | 거절 | 고장 |
|---|---|---|---|---|
| small-a (기준) | 178.8 (19.2) | 3.1 / 2 / 13 | 0 | 0 |
| surge-a (급증) | 226.8 (13.0) | **18.4 / 18 / 41** | 0 | 0 |
| fault-a (고장) | 178.2 (18.0) | 3.7 / 2 / 21 | 0 | 60 |

관찰(가설 아님, 기술):
- 급증 시나리오는 급증이 끝난 뒤 1200초가 지나도 대기 작업이 남아 있다. 포장 셀 1개의 예상 부하(급증 중 약 150%)와 맞는 방향이다.
- 고장 시나리오는 고장 구간에 포장 대기가 쌓였다가 복구 후 줄어드는 모습이 뷰어에서 보인다 (아래 캡처). 종료 시점 집계에서는 기준과 차이가 작다.

## 4. 남은 위험

- **FIFO 배정기는 아직 전체 상태를 읽는다.** 공개/비공개 분리는 로그 단계까지이고, 정책 입력 단계의 격리(관측 투영)는 #9 에서 한다.
- **고장 의미가 단순하다 (결정 0003).** 진행 작업을 끝까지 처리하므로 고장 영향이 과소평가될 수 있다.
- **셀 연결(material_flow)은 여전히 데이터로만 존재한다.** 흐름 제약은 검사하지 않는다.
- **처리량의 60% 가 기록 비용이다.** 실험 규모가 커지면 manifest 의 git 조회를 배치 단위로 한 번만 하도록 줄일 수 있다.
- **2D 뷰어는 정적 HTML** 이다. 사건이 수만 개로 늘면 SVG 크기가 커진다 (현재 약 45KB).
- 시드 30개는 근거 없는 임시 값이다.
