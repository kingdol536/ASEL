## 1. 질문

- **질문 A (배정 판단의 이식):** 코드 수정 없이 연결한 Claude 배정 정책(산업 중립 프롬프트)은 처음 보는 산업 환경
  (B 조립 라인, C IT 서비스)에서도 유효한 제안을 내고, 규칙 기반 배정보다 크게 나쁘지 않은가?
- **질문 B (구조 판단의 이식):** M5 에서 물류용으로 만든 구조 정책(P1/P2)은 C 에서 시간 초과를 4~7배 늘렸다(탐색적 관찰).
  같은 공개 관측을 받는 Claude 구조 제어는 이 실패를 피하면서, B 에서는 구조 변경의 이득을 얻는가?
  모델 크기(Haiku vs Sonnet)는 차이를 만드는가?

## 2. 가설과 반증 조건

모든 비교는 같은 시나리오·시드끼리의 **대응 차이**(처리 − 기준), 부트스트랩 95% 신뢰구간(CI).
주 지표는 환경별로 하나: **B = 작업 묶음 처리 시간 평균 `flow_mean_s`**, **C = 시간 초과로 취소된 요청 수 `orders_cancelled`**
(C 의 처리 시간 평균은 취소된 요청이 빠져 생존 편향이 있으므로 보조로만 쓴다). 둘 다 작을수록 좋다.

| ID | 질문 | 가설 | 반증 조건 |
|---|---|---|---|
| H1 | A | Claude 배정(Haiku)의 무효 제안 비율 < 1%, 대체(fallback) 비율 < 5% — B·C 각각 | 어느 환경에서든 시드 합산 비율이 기준 이상 |
| H2 | A | Claude 배정은 FIFO 보다 주 지표가 10% 넘게 나쁘지 않다 (비열등) — B·C 각각 | (Claude − FIFO) CI 상한 > FIFO 평균의 10% |
| H3 | B | C 에서 Claude 구조 제어(Haiku)는 P1 보다 취소가 적다 | (Claude-H − P1) CI 가 0 미만이 아님 |
| H4 | B | C 에서 Claude 구조 제어(Haiku)는 고정 구조(P0)보다 취소가 10% 넘게 많지 않다 (비열등) | (Claude-H − P0) CI 상한 > P0 평균의 10% |
| H5 | B | B 에서 Claude 구조 제어(Haiku)는 P0 보다 처리 시간이 짧다 | (Claude-H − P0) CI 가 0 미만이 아님 |
| H6 | B | Sonnet 구조 제어는 Haiku 보다 주 지표가 좋다 — B 또는 C 중 적어도 한 곳 | 두 환경 모두 (Sonnet − Haiku) CI 가 0 미만이 아님 |

- 여러 가설·환경을 동시에 보므로 **다중 비교** 문제가 있다. 위 6개만 확증적으로 해석하고 나머지(보조 지표, P2 비교 등)는 탐색적.
- 결과가 반증되면 부정적 결과로 그대로 보고한다. 정책을 결과를 보고 고치지 않는다.

## 3. 실험 조건

### 3.1 시나리오 (변경 없이 저장소의 파일 그대로)

- B: `scenarios/assembly-line-b.yaml` (3600s, 재구성 가능 셀 press-2, 셋업 90s)
- C: `scenarios/it-service-c.yaml` (1200s, 재구성 가능 셀 app-2 app↔worker, 워밍업 60s, 시간 초과 10/10/15s)
- 모든 수치는 가상 값이다.

### 3.2 팔(arm)

질문 A — 구조 제어 없음, 배정 정책만 바꾼다:

| 팔 | 배정 | 비용 |
|---|---|---|
| A-fifo | FIFO | 0 |
| A-order-age | 묶음 나이 순 | 0 |
| A-claude | Claude Haiku 5.5 (`claude-haiku-5-5`), 프롬프트 `v2-neutral`, effort low, max_tokens 2048 | API |

질문 B — 배정은 FIFO 고정, 구조 제어만 바꾼다:

| 팔 | 구조 제어 | 비용 |
|---|---|---|
| S-p0 / S-p1 / S-p2 | M4 의 고정·반응·비용 고려 (기준값 EXP-002 와 같음, 다시 조정하지 않음) | 0 |
| S-claude-haiku | Claude Haiku 5.5, 구조 프롬프트 `s1-neutral`, 모의 30s 에 한 번 이하 판단 | API |
| S-claude-sonnet | Claude Sonnet 5.5 (`claude-sonnet-5-5`), 나머지 같음 | API |

- Claude 구조 제어는 P0/P1/P2 와 **같은 공개 관측과 같은 전환 후보**를 받는다. 처리 시간·고장 원인·시간 초과 기한은 보지 않는다.
- 판단 기회가 다르다: P1/P2 는 사건마다, Claude 는 30s 에 한 번 이하 (비용 상한). 이것은 Claude 에 불리한 쪽의 차이다.
- 응답 캐시·예산 가드·실패 처리는 결정 0004 그대로. 실패한 판단은 배정이면 FIFO, 구조 제어면 '전환 안 함'으로 대체한다.

### 3.3 시드

- 파일럿: 개발 시드 0, 1 (분석하지 않음, 비용·시간 측정 전용)
- 평가: **300~329** (최대 30개). 개발 시드(0~9), EXP-001(0~1, 100~129), EXP-002(200~229)와 겹치지 않는다.
- 비용이 없는 팔(A-fifo, A-order-age, S-p0/p1/p2)은 항상 30개 전부 실행한다.

### 3.4 표본 크기 규칙 (파일럿 뒤 기계적으로 적용)

1. 파일럿으로 API 팔마다 실행당 평균 비용 c(장부 기준 USD)와 실행당 걸린 시간 w 를 잰다.
2. 쓸 수 있는 예산 R = $55 − (파일럿 직후 장부 지출) − $3 (여유분).
3. 우선순위 순으로 팔마다 N = min(30, floor(R_남은 / (1.2 × c))) 를 정하고 R_남은 에서 N × 1.2 × c 를 뺀다.
   우선순위: ① S-claude-haiku (B, C) → ② A-claude (B, C) → ③ S-claude-sonnet (B, C). 같은 순위 안에서는 B 다음 C.
4. 시간 제한: 모든 본 실행은 2026-11-18 18:00 (KST) 전에 끝나야 한다(크레딧 만료 11-19). 병렬 작업 수 J 로
   예상 시간이 넘으면 낮은 우선순위 팔부터 N 을 줄인다.
5. N 개 팔은 시드 300..300+N−1 을 쓰고, 그 팔과의 비교는 같은 시드만 쓴다.
6. **N < 10 인 팔은 설명적으로만 보고**하고 해당 가설은 "판정 불가"로 둔다. N < 3 이면 실행하지 않는다.
7. 정해진 N 과 계산 근거를 실행 전에 `experiments/reports/assets/EXP-003/sizing.json` 으로 커밋한다.

## 5. 분석 계획 (사전 고정)

- `asel compare` 의 대응 부트스트랩 (재표본 10,000회, 고정 시드 20261111).
- H1: 팔 전체 시드의 제안·대체 수를 합산한 비율.
- H2·H4: 비열등 한계 = 기준 팔 평균의 10%. CI 상한과 비교.
- H3·H5·H6: CI 가 0 미만이면 지지.
- 시드별 분포, 최악 사례, Claude 의 판단 이유(reason) 예시를 같이 공개한다.
- 비용: 팔별 총 USD·호출 수·실행당 비용. 실제 청구는 콘솔과 대조가 필요하다는 점을 밝힌다.

## 6. 한계 (미리 밝힘)

- 환경 2개(B 는 공통 언어 설계에 참고한 환경, C 는 동결 뒤 설계), 재구성 가능한 셀은 각 1개.
- Claude 와 규칙 정책의 판단 빈도가 다르다(§3.2). 비용 제약에서 온 설계이며 Claude 에 불리하다.
- 프롬프트는 각각 하나(`v2-neutral`, `s1-neutral`)만 쓴다. 프롬프트 민감도는 측정하지 않는다.
- 모델 응답은 녹화 시점 버전의 출력이다. 재생은 같은 사건 로그를 내지만, 같은 모델로 다시 녹화하면 다를 수 있다.
- 가격은 캐시된 표(2026-11-03)로 추정한다.
- 모든 수치는 가상이며 현실 공정·서비스 성능을 뜻하지 않는다.
