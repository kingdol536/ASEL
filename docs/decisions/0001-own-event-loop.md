# 0001. 논리 시뮬레이션 코어: 자체 이산 사건 루프

- 상태: **잠정** (2026-11-11)
- 관련: R-11, `docs/05` §4, `docs/08` §3, M1

## 맥락

M1의 목표는 작업·자원 상태가 어긋나지 않고, 같은 시드로 같은 논리 사건이 재생되는 세계 모델이다.
`docs/02`의 계약상 모든 상태 변경은 `propose → validate → apply → event` 한 경로를 거쳐야 하고,
`world_version`으로 오래된 요청을 걸러내야 한다.

## 후보안

| 안 | 장점 | 단점 |
|---|---|---|
| A. SimPy | 대기열·자원 모델이 이미 있음, 문서·사례 많음 | 상태 변경이 여러 프로세스(제너레이터)에 흩어짐 → 단일 변경 경로를 지키려면 감싸는 코드가 필요. 동시 사건 순서가 라이브러리 내부 규칙에 의존 |
| B. 자체 루프 | `(시각, 예약 순번)` 정렬로 동시 사건 순서를 직접 정의. 상태 변경을 `World.submit` 하나로 강제하기 쉬움 | 대기열·자원 기능을 직접 구현·테스트해야 함 |

## 선택과 이유

**B. 자체 루프** (`src/asel/core/simulator.py`, 약 100줄).
결정성과 단일 변경 경로가 M1의 통과 조건 그 자체이므로, 그 둘을 직접 통제할 수 있는 쪽을 택했다.

## 대안 포기 비용

선점 자원, 우선순위 대기열, 조건부 대기 같은 SimPy 기능을 필요할 때 직접 만들어야 한다.

## 위험

- 루프 자체의 버그. → 불변조건 검사, 속성 기반 테스트, 재생 테스트로 감시.
- 사건 수가 크게 늘면 성능. → M2 headless 반복 실행에서 `runs_per_min`을 측정.

## 검증 계획

- 같은 시드 2회 실행 시 이벤트 로그 바이트 동일 (`tests/test_reproducibility.py`)
- 이벤트 로그만으로 최종 상태 재구성 (`asel replay-check`)
- CI에서 Windows/Ubuntu 양쪽의 `events_sha256`을 출력해 플랫폼 간 일치 여부를 관측

## 재검토 조건

- 선점·복잡한 자원 정책이 필요해져 직접 구현 비용이 커질 때
- 이벤트 처리량이 실험 반복 수를 막는 병목으로 측정될 때
